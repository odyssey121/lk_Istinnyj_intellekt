## 2. Инструкция запуска

**Требования:** Docker и Docker Compose.

Из корня проекта:

```bash
docker compose up --build -d
```

При первом запуске будут собраны образы, создана база PostgreSQL, применены миграции и загружены демонстрационные данные. API запустится после подготовки базы и готовности mock-сервиса.

- Интерфейс: <http://localhost:8080>
- Документация REST API (Swagger): <http://localhost:8080/api/docs>

Демонстрационные пользователи:

| Роль | Email | Пароль |
|---|---|---|
| Администратор | `admin@ii.demo` | `DemoPass123!` |
| Клиент компании «Зёрна» | `client@zerna.demo` | `DemoPass123!` |
| Клиент компании «Баланс» | `client@balance.demo` | `DemoPass123!` |

Администратор видит все компании и может импортировать статистику. Клиент видит данные только своей компании.

Остановить приложение:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume. При запуске сервиса миграций seed выполняется повторно: он восстанавливает демонстрационные пароли и значения тестовых показателей за последние 90 дней, сохраняя существующие статусы отзывов и настройки импорта.

### Запуск тестов

Тесты используют отдельную PostgreSQL-базу. При первой подготовке, после запуска контейнера базы:

```bash
docker compose exec -T db createdb -U intelligence intelligence_test
export DATABASE_URL=postgresql://intelligence:intelligence@localhost:54329/intelligence_test
npm ci
npm run db:generate
npm run db:migrate
npm run db:seed
npm test
```

Для команд npm нужны Node.js 22 и npm. Команду `createdb` достаточно выполнить один раз. Для последующих запусков тестов достаточно `npm test`; база должна быть запущена, а порт 4001 — свободен для тестового mock-сервиса. Полная инструкция локальной разработки находится в `README.md`.

## 4. Краткое описание архитектуры

- **Frontend:** React, Vite, TypeScript, React Router и SWR. Отдельные разделы предназначены для аналитики, филиалов, отзывов и импорта.
- **Backend:** NestJS REST API. Функциональные модули отвечают за авторизацию, компании и филиалы, аналитику, отзывы, импорт и журнал обращений к источникам.
- **База:** PostgreSQL и Prisma. Основные сущности — компании, пользователи, филиалы, ежедневные показатели, отзывы, настройки импорта и журнал запросов. Структура задаётся миграциями; `prisma/seed.ts` создаёт тестовые данные.
- **Разграничение доступа:** JWT хранится в HttpOnly cookie. Backend получает актуальные роль и компанию пользователя из базы и ограничивает запросы к филиалам, показателям и отзывам. Все компании доступны только администратору.
- **Импорт статистики:** администратор задаёт полный URL источника и метод GET или POST. Отдельный mock-сервис имитирует внешний API. Ответ проверяется перед записью, повторный импорт обновляет показатели без дубликатов.
- **Журнал:** запросы, ответы, повторные попытки и ошибки внешнего источника сохраняются в PostgreSQL. Просмотр журнала доступен администратору.
- **Запуск:** Docker Compose поднимает PostgreSQL, миграции с seed, mock-сервис, NestJS API и nginx с собранным frontend. Nginx предоставляет интерфейс и API через один origin.

## 5. Известные ограничения

- Данные и внешний источник демонстрационные; подключения к реальным геосервисам нет. Показатели не разделены по геосервисам.
- Нет регистрации и восстановления пароля, интерфейсов управления компаниями и пользователями. Checkbox «Запомнить меня» представлен без логики сохранения.
- Импорт запускается вручную администратором и выполняется синхронно в HTTP-запросе; планировщика и фоновой очереди нет. Один импорт ограничен периодом в 90 дней.
- При двух заданных датах период аналитики и списка отзывов ограничен 90 днями. Пустые даты позволяют получить данные за всё доступное время.
- Настройка URL и метода источника общая для всех компаний. Возможность задать отдельный источник для каждой компании не реализована.
- Полные тела запросов и ответов источников хранятся в PostgreSQL без автоматической очистки; объём журнала будет расти.
- Выход удаляет cookie, но серверного списка отозванных JWT нет: скопированный действующий токен остаётся действительным до истечения срока.
- Значения JWT-секрета и учётные записи в конфигурации предназначены для демонстрации. Перед использованием с реальными данными необходимы собственный секрет, корректный `APP_ORIGIN`, HTTPS с `COOKIE_SECURE=true` и настройка ограничений исходящих запросов к внешним источникам.
- Текущий Docker Compose с одним экземпляром API и PostgreSQL предназначен для локального запуска и не обеспечивает отказоустойчивость production-системы.

## 6. План развития для 500+ компаний

Расчётный сценарий: **500 компаний, 5 000 филиалов**, один источник и одна запись показателей на филиал в день. Это около **1,825 млн записей в год**, или 5,475 млн за три года. Количество отзывов, размер журналов и одновременная нагрузка зависят от фактического использования. Для раздельного хранения нескольких геосервисов потребуется добавить измерение источника в модель показателей и изменить уникальный ключ.

Ниже — предлагаемое развитие, а не уже реализованные возможности или подтверждённая производительность.

### 6.1. База данных и индексы

В текущей схеме уже есть `Branch(companyId)`, уникальный индекс `DailyMetric(branchId, date)`, `Review(branchId, date)` и `ImportLog(createdAt, id)`. Их сохраняем: они помогают находить филиалы компании, показатели филиала за период и страницы журнала.

На стенде с реалистичным объёмом данных сначала собираем статистику через `pg_stat_statements` и сравниваем планы `EXPLAIN (ANALYZE, BUFFERS)`. Затем проверяем такие дополнительные индексы:

```sql
-- Сводка и график администратора по всем филиалам за период.
CREATE INDEX CONCURRENTLY "DailyMetric_date_branchId_idx"
ON "DailyMetric" ("date", "branchId");

-- Отзывы конкретного филиала, включая сортировку date DESC, id ASC.
CREATE INDEX CONCURRENTLY "Review_branchId_date_id_idx"
ON "Review" ("branchId", "date" DESC, "id" ASC);

-- Та же выборка с фильтром по статусу.
CREATE INDEX CONCURRENTLY "Review_branchId_status_date_id_idx"
ON "Review" ("branchId", "status", "date" DESC, "id" ASC);
```

Индекс по дате показателей полезен, когда выбран период по многим филиалам; существующий индекс начинается с `branchId` и подходит для конкретного филиала. Индексы отзывов рассчитаны на выборку одного филиала; для компании с несколькими филиалами PostgreSQL может всё равно выполнять дополнительную сортировку. Пользу каждого индекса нужно подтвердить замерами, поскольку индексы занимают место и замедляют запись. Индекс по рейтингу добавлять только при частом использовании этого фильтра и подтверждённой пользе.

`CREATE INDEX CONCURRENTLY` выполнять отдельным шагом миграции вне транзакционного блока, с контролем результата и возможностью безопасного повторного запуска. Старый индекс не удалять до проверки, что новый действительно его заменяет для рабочих запросов.

Списки компаний и филиалов перевести на серверную пагинацию и поиск. Сейчас доступные филиалы загружаются целиком и фильтруются в браузере. Для журнала и отзывов при больших страницах перейти от `OFFSET` к курсору по стабильной паре даты и ID.

### 6.2. Кэш аналитики

После оптимизации SQL добавить Redis для повторных запросов `GET /api/analytics/summary` и `GET /api/analytics/timeseries`:

1. Сначала сервер проверяет сессию и доступ к компании и филиалу через `Scope`. Только затем формирует ключ кэша.
2. Ключ включает тип запроса, эффективную область доступа (`company:<id>` или `admin:all`), ID филиала либо `all`, нормализованные даты либо `all`, формат ответа и версию данных. Например: `analytics:v1:company:1:branch:2:from:2026-11-01:to:2026-11-30:summary:ver:15`.
3. При попадании возвращается сохранённый JSON; при промахе данные читаются из PostgreSQL и сохраняются в Redis с **TTL 60 секунд**. Если Redis недоступен, API обращается к PostgreSQL напрямую.
4. Во избежание одновременного пересчёта одного ключа экземпляры API используют короткую блокировку `SET NX PX` с уникальным токеном владельца. Блокировку снимает только владелец; при её истечении повторный расчёт допустим.

Чтобы импорт не оставлял устаревшие данные в кэше, добавить в PostgreSQL версии аналитики: отдельную версию на компанию и общую для запросов администратора по всем компаниям. При сохранении показателей импорт **в той же транзакции**, что и upsert метрик, увеличивает версию затронутой компании и общую версию. При создании, удалении или изменении оценки, даты либо филиала отзыва версии также увеличиваются; при переносе между компаниями — у обеих компаний и общей области. Изменение только статуса обработки отзыва не влияет на сводку и график и не требует их сброса.

Перед чтением кэша API получает нужную версию из основной PostgreSQL и включает её в ключ. После успешной транзакции новые запросы используют новую версию, а старые ключи истекают сами. Общая версия может стать точкой конкуренции при высокой частоте записей: её ожидания нужно измерять и увеличивать один раз на пакет импорта, а не на каждую дневную запись.

При дальнейшей нагрузке можно предрассчитывать показатели по компании и дню. Для рейтинга хранить **сумму оценок и число отзывов**, чтобы правильно получать средний рейтинг. Исправленный импорт должен пересчитывать затронутый день, а не повторно прибавлять старые значения.

### 6.2.1. Отдельная база для аналитики

При росте объёмов и сложности отчётов можно подключить аналитическое хранилище, например ClickHouse. PostgreSQL остаётся основной базой пользователей, прав и исходных данных; показатели передаются в ClickHouse через очередь или CDC и используются для тяжёлых агрегатов.

Перед внедрением нужно нагрузочно сравнить этот вариант с оптимизированным PostgreSQL. При синхронизации важно учитывать повторы и исправления данных, контролировать задержку и сохранять проверку доступа к компаниям через API. Например, дедупликация `ReplacingMergeTree` происходит асинхронно, поэтому при расчётах необходимо учитывать версии строк. Подробнее: [дедупликация в ClickHouse](https://clickhouse.com/resources/engineering/clickhouse-optimize-table-final).

### 6.3. Журнал запросов и ответов

При росте объёма журналов метаданные обращений оставить в PostgreSQL, а полные тела запросов и ответов перенести в закрытое объектное хранилище, например MinIO. Доступ к просмотру сохранится только у администратора через API.

Новые тела сначала сохранять во временном поле PostgreSQL, затем загружать в хранилище фоновым worker. После проверки размера и контрольной суммы сохранять ссылку и удалять временную копию. Существующие записи переносить пакетами по тому же принципу. Автоматическое удаление истории не включать до согласования срока хранения.

### 6.4. Импорт, доступность и проверка

Массовый импорт перенести из синхронного HTTP-запроса в очередь Redis с отдельными workers. `POST /api/imports/statistics` должен создавать задачу и возвращать `202` с `jobId`, отдельный маршрут — показывать её состояние. Задачу и событие постановки сохранять через transactional outbox, ограничивать параллельность по источнику, учитывать его квоты и `Retry-After`. Для пересекающихся импортов одного филиала обеспечить последовательное выполнение или контроль версии данных.

Запустить несколько экземпляров NestJS за балансировщиком, вычислить общий бюджет соединений PostgreSQL для API и workers, настроить резервные копии и проверку восстановления. Текущую серверную проверку компании применять также к новым маршрутам задач и чтению кэша.
